# xkop

Маршрутизатор трафика для OpenWrt на движке [Xray-core](https://github.com/XTLS/Xray-core).

Роутер должен **распределять** трафик, а не гнать его весь в туннель.
Заблокированное идёт через прокси, остальное — напрямую, и решение принимается
по спискам имён и адресов, а не по принципу «всё или ничего». На живом роутере
это выглядит так: две трети трафика не платят ни за шифрование, ни за крюк
до узла и обратно.

## Состояние

**Работает на живом роутере.** Cudy TR3000, OpenWrt 25.12, пять узлов подписки,
трафик распределяется, выбор узла держится и не скачет.

Собрано целиком: подписки с кэшем и состояниями, генерация конфигурации
(её принимает или отвергает сам движок), служба с порядком запуска
по инвариантам, правила nftables и политика маршрутизации, DNS-слой с FakeIP
и Канарейкой, разбор маршрута по журналу доступа, обновление пакетами
с откатом, LuCI и отдельная панель для конечного пользователя.

Пакеты собираются под восемь архитектур: `aarch64` (cortex-a53, cortex-a72,
generic), `arm` (cortex-a7 neon-vfpv4, cortex-a9 neon), `mips_24kc`,
`mipsel_24kc`, `x86_64`. Формат — `apk`; ветка `ipk` для OpenWrt 23–24 готова,
но ещё не собиралась.

## Установка

```sh
sh <(wget -O - https://github.com/Jedakaya/xkop/releases/latest/download/install.sh)
```

Установщик берётся из релиза, а не с ветки, намеренно: `raw.githubusercontent`
отдаёт файл с пограничного кэша и параметры запроса игнорирует, поэтому
исправленный скрипт ещё несколько минут приезжает старым. Файл релиза привязан
к тегу и подменён быть не может.

Что он делает: ставит зависимости, движок под архитектуру роутера, сам xkop,
LuCI и панель клиента, а в конце проверяет сам себя. Если на роутере стоит
podkop — снимает его вместе с движком, возвращает резолверы dnsmasq на место
и **переносит пользовательские списки**: свои домены и подсети переезжают
сами, вводить их заново не нужно.

Дальше остаётся вставить ссылку подписки:

```sh
uci set xkop.main.url='https://ваша-ссылка' && uci commit xkop
/etc/init.d/xkop enable && /etc/init.d/xkop start
```

Обновление — одной командой, с подготовленным заранее откатом:

```sh
xkop update
```

Настройки целиком — в LuCI, «Сервисы → xkop». Панель для домашних, где нет
ничего кроме подписки и выбора маршрута, — на порту 8090.

## Как это устроено

Имя решается один раз, при резолве. Домены из выбранных списков получают
поддельный адрес из диапазона FakeIP, и дальше этот адрес сам приводит
соединение в движок — сниффинг на каждом соединении не нужен. Адреса, которые
по имени не опознать (Telegram ходит на захардкоженные, сайт за CDN — тем
более), ловятся подсетями в наборе nftables.

Всё остальное идёт мимо userspace обычным форвардингом ядра.

Инварианты запуска куплены отказами на живом железе: задачи по расписанию
встают до генерации конфигурации, невалидная конфигурация не устанавливается,
но и не отменяет запуск, кэш подписки — источник истины при старте, неудачное
обновление не имеет права ухудшить рабочее состояние.

## Что отличает

**Канарейка** — обнаружение подмены DNS. Спрашивает то, чего не может
существовать, и по ответу узнаёт адрес заглушки провайдера. Выученное движок
дальше отбраковывает сам, откуда бы оно ни пришло. Канарейка отвечает только
за обнаружение; решение принимают уровни выше.

**Узел не скачет.** Переход на другой узел происходит, когда прежний умер или
его задержка выросла за порог, а не от шума измерения. Ручное закрепление
переживает перезапуск движка.

**Разбор маршрута.** `xkop explain <домен>` отвечает, куда ушёл этот домен
и почему: совпало правило или не совпало ни одного, во что имя разрешилось,
поддельный ли адрес и попадает ли он в перехват.

**Подписки как сущность.** Несколько подписок сливаются в один пул, формат
выбирается путём (`/json`, `/v2ray-json`), заголовки устройства передаются,
а отказ панели — лимит устройств, срок — показывается её же словами,
а не додумывается.

**Своя реализация на Xray-core**: XHTTP, REALITY, Hysteria2 без сторонних форков
движка.

Списки имён и подсетей — из
[itdoginfo/allow-domains](https://github.com/itdoginfo/allow-domains),
25 категорий. Свои списки можно добавить строками или ссылкой; список по ссылке
принимается и обычным текстом, и документом JSON.

## Что нужно роутеру

OpenWrt с `nftables` и `kmod-nft-tproxy`. Зависимости ставит установщик:
`curl`, `jq`, `gzip`, `coreutils-base64`, `bind-dig`. Движку нужно около 34 МБ
на флэш и порядка 50 МБ оперативной памяти в работе.

Конфликтует с `podkop`, `luci-app-passwall`, `luci-app-passwall2`,
`https-dns-proxy`, `nextdns` — они делают то же самое и мешают друг другу.

## Если что-то не так

```sh
xkop global_check            # всё сразу и одной строкой, что не так
xkop explain example.com     # куда ушёл этот домен и почему
xkop nodes                   # узлы: состояние, задержка, сколько проверок
logread -e xkop              # журнал
```

## Разработка

```sh
sh tests/run.sh                      # 22 набора, роутер не нужен
XRAY=/путь/к/xray sh tests/run.sh    # плюс приёмка конфигурации живым движком
JQ=/путь/к/jq sh tests/run.sh        # если jq в системе нет
```

На роутере — отдельная проверка, и она обязательна после каждой правки:

```sh
scp tools/smoke.sh root@роутер:/tmp/ && ssh root@роутер sh /tmp/smoke.sh
```

Она смотрит не на наличие, а на содержимое: сколько адресов в наборе
перехвата, сколько правил в конфигурации, читаются ли списки из uci
в строгом режиме, возвращаются ли правила, если запуск службы попал
на занятый замок. Оффлайновые проверки этот класс не видят по устройству —
в них всё, что трогает роутер, подменено заглушками.

Набор правил nft читается настоящим `nft -c` в CI. Регулярные выражения в jq
не используются: в OpenWrt он собран без oniguruma, и `test`, `match`, `gsub`
там не существуют.
