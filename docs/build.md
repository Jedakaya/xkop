# Сборка и проверка на роутере

## Что пересобирается и как часто

Три вещи с совершенно разной частотой изменений, и смешивать их в одну сборку
значит платить временем за каждую правку скрипта.

| Что | Когда пересобирается | Где |
|---|---|---|
| образ SDK | при смене релиза SDK, раз в несколько месяцев | `sdk-images.yml` |
| пакет движка | при подъёме версии Xray | отдельно, см. `install.md` |
| пакет xkop | когда меняется содержимое пакета | `build.yml` |

Медленное в сборке — распаковка SDK и обновление фидов, минуты. Это вынесено
в готовый образ, который лежит в GHCR и к нашему коду отношения не имеет.
Сборка самого пакета после этого — один вызов `make`.

Первый прогон: запустить `sdk-images.yml` вручную, дальше он сам нужен только
при правках в `sdk/`.

## Пакет xkop

| Формат | SDK | Куда ставится |
|---|---|---|
| `.apk` | `openwrt/sdk:x86-64-25.12.0` | OpenWrt 25 и новее |
| `.ipk` | `openwrt/sdk:x86-64-24.10.8` | OpenWrt 23 и 24 |

Образы SDK **закреплены на релизах, а не на SNAPSHOT**: SNAPSHOT пересобирается
каждый день, и сборка, которую нельзя повторить через месяц, — не сборка.

Пакет объявлен `PKGARCH:=all`, поэтому x86_64 SDK выдаёт файл, который ставится
на любую архитектуру. От SDK зависит только формат пакета, не процессор.
С движком так не выйдет: он бинарный, и пакет для него нужен под каждую
архитектуру отдельно.

Локально, если есть Docker:

```sh
docker build -f Dockerfile-apk --build-arg XKOP_VERSION=0.20082026 -t xkop:apk .
docker create --name apk xkop:apk
docker cp apk:/builder/bin/. ./bin/raw/
docker rm apk
find ./bin/raw -name 'xkop*.apk'
```

В CI то же самое делает `build.yml`: по кнопке (`workflow_dispatch`) кладёт
пакеты в артефакты, по тегу — дополнительно создаёт релиз.

**Тег нужен только когда меняется содержимое пакета.** Ни проверки на роутере,
ни правки скриптов тега не требуют — для них есть выкладка копированием.

## Проверки в CI

- `tests.yml` — те же `tests/run.sh`, что и локально, плюс три сторожа:
  в jq-программах не должно быть регулярных выражений (в OpenWrt jq собран
  без oniguruma), скрипты должны разбираться `sh -n`, и ни один файл пакета
  не должен приехать с CRLF — иначе на роутере получится `bad interpreter`.
- `shellcheck.yml` — разбор изменений shellcheck'ом, только по ошибкам.

## Установка на роутер

Тем же способом, что и у клиента, — установщиком с GitHub:

```sh
sh <(wget -O - https://github.com/Jedakaya/xkop/releases/latest/download/install.sh)
```

Из релиза, а не с ветки: `raw.githubusercontent` отдаёт файл с пограничного
кэша, и исправленный установщик приезжает старым ещё несколько минут после
пуша. На этом потеряно шесть попыток установки подряд с одной и той же
ошибкой в одной и той же строке.

Он ставит пакетами, если есть релиз с пакетом под архитектуру роутера,
и файлами с ветки, если релиза ещё нет. Второй путь честно называется
в выводе: у него нет версии, только хэш коммита.

Принудительно с ветки, не глядя на релизы:

```sh
XKOP_FROM_BRANCH=1 sh <(wget -O - https://raw.githubusercontent.com/Jedakaya/xkop/main/install.sh)
```

## Проверка на роутере без пакета

Пакет для этого не нужен. Файлы кладутся напрямую:

```sh
tools/deploy-dev.sh root@192.168.1.1
```

Скрипт копирует `/usr/bin/xkop` и `/usr/lib/xkop/*`, ставит бит запуска
и подставляет версию `dev`. `/etc/config/xkop` **не трогается**, если
не передать `--config`: это единственный файл на роутере, где лежит
не наше состояние.

## Движок на стенде

Постоянной поставки движка ещё нет — она описана в `install.md` и делается
пакетом. Для стенда есть короткий путь: `tools/install-xray-dev.sh`
запускается **на роутере** и кладёт официальный бинарник XTLS.

```sh
scp tools/install-xray-dev.sh root@192.168.1.1:/tmp/
ssh root@192.168.1.1 'sh /tmp/install-xray-dev.sh'
```

Из правил, купленных отказами, скрипт соблюдает те, что имеют смысл и здесь:
архив качается в `/tmp`, то есть в RAM, и неудача не стоит ни байта флэша;
место проверяется после загрузки и до установки, по реальному размеру файла,
а не по константе; результат доказывается запуском, а не кодом возврата `cp`.
Файлы geoip и geosite из архива не распаковываются — это большая часть
из его 19 МБ, а для проверки метрик они не нужны.

Если флэша мало, движок можно вообще не класть на диск:

```sh
XRAY_TARGET=/tmp/xray sh /tmp/install-xray-dev.sh
```

Версия по умолчанию — `v26.7.28`. Перебивается переменной:
`XRAY_VERSION=v26.3.27 sh install-xray-dev.sh`.

Раньше здесь стояла `v26.3.27` с объяснением «самая свежая, которую XTLS
не пометил как предварительную». Правило оказалось негодным: проверено
по API — **все** релизы после v26.3.27 помечены предварительными, месяцами
подряд, и клиенты, которыми люди пользуются, давно ушли вперёд. Следовать
этой метке значило стоять на месте.

Версия по-прежнему поднимается руками и после проверки, но повод для этого —
проверка, а не флаг в чужом релизе.

## Проверка команды stats на живом Xray

Обвязки ещё нет, поэтому Xray для проверки запускается руками с минимальной
конфигурацией `tools/xray-stats-test.json`. Она никого не маршрутизирует:
локальный socks на 10808, метрики на 11111 и наблюдение за исходящим `direct`.

```sh
scp tools/xray-stats-test.json root@192.168.1.1:/tmp/
ssh root@192.168.1.1
xray run -c /tmp/xray-stats-test.json &

xkop stats
```

Что должно получиться сразу:

- `ok` равно `true`, `error` равен `null`;
- `distribution` весь нулевой — трафика ещё не было;
- `observatory.state` равен `active`, а узел `direct` в состоянии `pending`:
  проверок ещё не было, и это именно «проверяется», а не «мёртв».

Через минуту-другую узел `direct` должен перейти в `alive` с задержкой
в `delay_ms`. Если прогнать через socks что-нибудь тяжёлое, появятся счётчики:

```sh
curl -x socks5h://127.0.0.1:10808 -o /dev/null https://speed.hetzner.de/10MB.bin
xkop stats
```

Тогда в `traffic.outbound.direct` вырастут байты, а `distribution.direct.share`
станет единицей.

Отдельно стоит проверить ветки отказа — они на роутере ведут себя иначе, чем
на заглушке:

```sh
kill %1        # движок остановлен
xkop stats     # ожидается error: engine_not_running
```

Если Xray работает, а метрики выключены, ожидается `metrics_unreachable`.
Различать эти два случая — смысл команды, и это то, что проверяется здесь
в первую очередь.
