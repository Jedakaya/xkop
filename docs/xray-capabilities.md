# Возможности Xray, которые стоит использовать

Найдено при разборе документации и обсуждений. Отмечено, что подтверждено
источником, а что требует проверки на железе.

## Слой данных для дашборда — вопрос закрыт

Отдельный gRPC-клиент на роутере не нужен.

**Счётчики трафика по каждому исходящему**, включая `direct` и `block`:

```
outbound>>>main>>>traffic>>>uplink
outbound>>>direct>>>traffic>>>downlink
outbound>>>block>>>traffic>>>downlink
```

**Задержки по каждому узлу** — observatory ведёт `health_ping`.

**Всё отдаётся одним HTTP-эндпоинтом**: при включённой функции метрик
доступен `http://127.0.0.1:11111/debug/vars`, обычный JSON. Читается `curl`
и `jq`, без gRPC и без моста поверх `xray api`.

Это на порядок проще интеграции с Clash API, которую мы считали основной
издержкой перехода.

## Карантин мёртвых серверов — нативный

Балансировщик со стратегиями `leastPing`, `leastLoad`, `roundRobin`, `random`.
При заданном `fallbackTag` и включённом observatory узлы, признанные
недоступными, **исключаются автоматически**.

То есть карантин, который мы собирались строить сами, уже есть в движке.
Нам остаётся его показать пользователю.

Здоровье узлов настраивается через `burstObservatory.pingConfig`: адрес
проверки, интервал, таймаут, параметры выборки.

**Известное ограничение:** динамически зарегистрированные исходящие до десяти
минут остаются без данных наблюдения, и балансировщик их не видит. Значит
после обновления подписки новые серверы вступают в игру не мгновенно —
это надо либо учесть в интерфейсе, либо обойти перезапуском observatory.

## Фрагментация ClientHello — самое важное

У исходящего `freedom` есть `fragment`: разбиение TLS ClientHello на части.
Рекомендованная отправная точка — `packets: "tlshello"`, плюс `length`
и `interval`. Фрагментируется только рукопожатие, остальное соединение
не трогается, накладные расходы разовые.

Это ломает DPI, который блокирует по SNI.

**Почему это меняет продукт.** Сегодня сайт, заблокированный по SNI, можно
открыть только через туннель. С фрагментацией он открывается **напрямую** —
без прокси, без оплаченного трафика, без задержки на плечо до сервера.

Тезис проекта — распределять трафик, а не гнать всё в туннель. Фрагментация
двигает границу в нужную сторону: часть того, что раньше требовало туннеля,
перестаёт его требовать.

Для владельца, платящего за серверы, это прямая экономия трафика.

Проверяемо на нашем же случае: `fakeip.podkop.fyi` у провайдера пользователя
режется именно по SNI — TCP соединяется, а сброс приходит в рукопожатии.
Если фрагментация его открывает, механизм работает.

**Требует проверки на железе.** Фрагментация помогает не против каждого DPI,
и агрессивные варианты (разбиение на 6 байт, цепочки через `dialerProxy`)
дают накладные расходы. Начинать с `tlshello` и измерять.

Отдельно есть внесение шума в UDP — против DPI, анализирующего QUIC.

## ECH — шифрование самого SNI

Фрагментация ломает разбор SNI. ECH его **прячет**: имя узла в ClientHello
шифруется целиком, и DPI видеть его нечего.

Xray это умеет. Ключ и конфиг генерируются командой
`xray tls ech --serverName example.com`. Клиент включает ECH непустым
значением ECHConfig, и поддерживаются два способа его получить: строкой
в конфигурации либо запросом к DNS. Сервер при этом продолжает принимать
и обычные соединения без ECH.

**Где это работает у вас.** Ваши собственные серверы вы контролируете через
панель — значит ECH на них включается, и провайдер перестаёт видеть, что
соединение идёт к VPN-узлу. Это защита не от блокировки конкретного сайта,
а от определения самого факта туннеля по SNI.

**Где не работает.** Для прямых соединений с чужими сайтами ECH нужен на их
стороне. Поэтому он дополняет фрагментацию, а не заменяет её: ECH — для наших
узлов, фрагментация — для чужих.

**Конфликт, который надо не проглядеть.** Получение ECHConfig через DNS
использует записи HTTPS. А мы одновременно хотим отклонять записи HTTPS,
чтобы ломать автообнаружение DoH браузерами. Одно рубит другое.

Разрешение: отклонять HTTPS только для клиентских запросов, но не для
собственных запросов роутера, либо использовать ECHConfig строкой
в конфигурации, раз наши узлы известны заранее.

## Постквантовое шифрование VLESS

В VLESS есть обёртка ML-KEM-768 в связке с X25519. Постквантовый обмен
ключами на домашнем роутере — вещь, которую почти никто не включает.

Практическая ценность сегодня умеренная, но она есть и она реальна: трафик,
записанный сейчас, не расшифруют позже. Для тех, кому это важно, это
единственный аргумент, который вообще имеет значение.

Включается со стороны сервера и клиента, стоит проверить совместимость
с панелью.

## Прочее, отмеченное на будущее

- `sockopt` с привязкой к интерфейсу — пригодится при нескольких WAN;
- `dialerProxy` — цепочки исходящих, в том числе для многоступенчатой
  фрагментации;
- `queryStrategy` — управление A и AAAA на уровне сервера DNS.
