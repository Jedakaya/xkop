# Команда `stats`

Реализована. Читает метрики Xray и отдаёт нормализованный JSON. Ни панель,
ни LuCI не знают ни формата Xray, ни адреса его эндпоинта — см.
`cli-contract.md`.

Код: `xkop/files/usr/lib/xkop/stats.sh` (доступ и отказы),
`xkop/files/usr/lib/xkop/stats.jq` (нормализация). Проверки:
`tests/run.sh`.

## Конверт

Набор ключей одинаков при успехе и при отказе — потребитель не должен
проверять наличие полей.

```json
{
  "ok": true,
  "error": null,
  "detail": null,
  "source": { "address": "127.0.0.1:11111", "collected_at": 1755600000 },
  "traffic": { "outbound": {}, "inbound": {}, "outbound_total": {} },
  "distribution": {},
  "observatory": { "state": "active", "nodes": [] }
}
```

При отказе `ok` равен `false`, `error` содержит код, `detail` — установленные
факты, а `traffic`, `distribution` и `observatory` равны `null`.

**Код возврата всегда ноль**, если команда отработала. Недоступность метрик —
это содержимое, а не код возврата.

## Коды отказа

| Код | Что установлено |
|---|---|
| `engine_not_running` | соединение не удалось **и** процесса движка нет |
| `metrics_unreachable` | процесс движка есть, но соединения нет — метрики выключены или заняты |
| `metrics_bad_response` | ответ не 200 либо тело не разбирается |
| `metrics_no_stats` | пришёл валидный JSON без `stats` — на порту не Xray |

Разделение первых двух стоит одного `pgrep` и снимает главную ошибку podkop:
интерфейс не должен додумывать причину, а по одному отказу сокета мёртвый
движок и выключенные метрики неразличимы.

`detail` содержит только измеренное: `address`, `http_code`, `curl_exit`.

## Трафик

`traffic.outbound` и `traffic.inbound` — по тегу, `{uplink, downlink, total}`
в байтах. `traffic.outbound_total` — сумма по исходящим, то есть то, что
действительно ушло с роутера. Именно поэтому это не сумма по входящим: числа
не совпадают, а ключ с именем `total` заставил бы интерфейс гадать.

Счётчики **накопительные с момента запуска движка** и чтением не сбрасываются
(проверено по `app/metrics/metrics.go`: берётся `counter.Value()`). Суточные
цифры дашборда считаются разностью снимков — это отдельная задача, не эта
команда.

## Распределение

`distribution` — байты и доля по ролям: `direct`, `proxy`, `blocked`,
`service`. Это то самое число главного экрана: ушло ли всё в туннель.

Роль выводится из тега исходящего. Зарезервированы: `direct` — напрямую,
`block` — заблокировано, `dns-out`, `metrics-out`, `api` — служебные.
Остальное — прокси. **Генератор конфигурации обязан этих имён держаться**,
иначе распределение поедет.

Служебная роль показана отдельно, а не размазана по остальным, чтобы сумма
долей сходилась и никого не приходилось подгонять.

## Узлы

`observatory.state` — `active` или `disabled`. Выключенный observatory это
не «узлов нет», и путать эти два состояния нельзя.

Состояние узла (`nodes[].state`):

| Состояние | Значение |
|---|---|
| `alive` | движок считает узел пригодным |
| `dead` | все попытки в окне наблюдения провалились |
| `pending` | данных наблюдения ещё нет — узел добавлен недавно |
| `unobserved` | трафик по тегу есть, а наблюдения по нему нет вообще |

`pending` существует ровно ради известного ограничения Xray: свежий узел до
десяти минут без данных, и `alive` у него вычисляется как `all != fail`, то
есть при нуле проверок выходит `false`. Показать это как «мёртв» — соврать.

## Единицы и ловушки движка

Проверено по исходникам Xray, а не выведено из документации:

- `OutboundStatus` сериализуется через `encoding/json` с `omitempty`. Поле со
  значением `false` или `0` **отсутствует**, а не приходит нулём. Отсутствие
  `alive` означает `false`, а не «неизвестно».
- `burstObservatory` заполняет `health_ping`, и все длительности внутри него —
  **наносекунды** (`time.Duration`, приведённый к `int64`). При этом соседнее
  поле `delay` — миллисекунды. Перепутать эти две единицы здесь проще всего.
- Обычный `observatory` поля `health_ping` не заполняет вовсе, а мёртвому узлу
  пишет `delay` равным `99999999`. Это признак, а не задержка, и наружу он
  не выходит: `delay_ms` в таком случае `null`.

Нормализация приводит всё это к `delay_ms`, `average_ms`, `min_ms`, `max_ms`,
`deviation_ms` в миллисекундах с точностью до десятой. Поле `source`
показывает, откуда данные: `health_ping` или `probe`.

## Проверки

`tests/run.sh` прогоняет нормализатор по записанным ответам эндпоинта и
сличает с зафиксированным контрактом. Роутер и живой движок не нужны:
в образцах воспроизведены и пропуски `omitempty`, и обе реализации
observatory.

```sh
sh tests/run.sh            # jq из PATH
JQ=/path/to/jq sh tests/run.sh
```

Образцы: `tests/fixtures/metrics/`, ожидаемый вывод: `tests/expected/metrics/`.
Ветки отказов (недоступный эндпоинт, 404, не-JSON, отсутствие движка)
проверялись вживую поднятым HTTP-заглушкой, автотестом пока не покрыты.
