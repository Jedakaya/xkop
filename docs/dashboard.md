# Дашборд

## Чем он отличается от podkop

Не оформлением. Podkop-подобность возникает из **информационной модели**:
там дашборд это список серверов с пингами, то есть вид на состояние движка.
Перекрасить его недостаточно — получится тот же список другого цвета.

Главный вопрос пользователя не «какой пинг у третьего сервера». Главный
вопрос — **правильно ли сейчас распределяется трафик**. Это и есть работа
роутера, и именно её надо показывать.

## Главный экран: распределение трафика

Xray считает трафик по каждому исходящему отдельно, включая `direct`
и `block`. Значит показать можно не обещание, а факт:

```
За сегодня через роутер прошло 12.4 ГБ

  напрямую        9.8 ГБ   79%
  через туннель   2.4 ГБ   19%
  заблокировано   0.2 ГБ    2%
```

Ни podkop, ни netshift этого не показывают, потому что показывают состояние
движка, а не результат работы.

Практическая ценность выше эстетической: если через туннель ушло 100%,
значит списки не применились и в VPN идёт всё подряд. Сегодня такое
обнаруживается по жалобе клиента, а не по экрану.

Для владельца, платящего за серверы, эта же цифра — расход.

## Пул серверов, а не список пингов

Показывается состояние пула: сколько живых, сколько в карантине, какой
активен сейчас и **почему выбран именно он**.

Задержки — деталь второго уровня, они раскрываются по требованию. На главном
экране число «7 из 9 живы» полезнее девяти чисел в миллисекундах.

Карантин ведёт сам движок: балансировщик с `fallbackTag` исключает узлы,
признанные недоступными. Наша задача — показать это, а не считать заново.

**Учесть:** после обновления подписки новые узлы до десяти минут не имеют
данных наблюдения. В интерфейсе это состояние «проверяется», а не «мёртв»,
иначе выглядит как поломка.

## Проблемы всплывают на месте

Отдельной вкладки диагностики нет. Экран, который надо не забыть открыть, —
это способ узнавать о поломках последним.

Подписка не обновилась — видно в блоке подписки. DNS перехвачен — видно
в блоке DNS. Сервер выпал — видно в пуле.

Общее состояние — одна строка сверху: работает, работает с оговорками,
не работает. С причиной, а не с пятью зелёными галочками, которые пользователь
должен интерпретировать сам.

## Разбор маршрута — главная функция

Поле ввода домена и ответ на вопрос, который задают чаще всех остальных
вместе взятых: **почему этот сайт ведёт себя так, а не иначе**.

```
youtube.com

  DNS        ответил 127.0.0.10 за 4 мс, FakeIP 198.18.3.41
  Совпало    geosite: youtube
  Правило    «Заблокированное» -> туннель
  Канал      подписка Main, узел NL-Amsterdam-2, 42 мс
  Итог       идёт через туннель

  За сутки: 312 запросов, 1.2 ГБ
```

Нигде такого нет. Роутеры показывают, что настроено, а не что произошло
с конкретным именем.

Ценность не в красоте. Это перевод поддержки в самообслуживание: вместо
«у меня не открывается, посмотри» клиент сам видит, что домен не попал
ни в один список и ушёл напрямую. И вы это видите тем же экраном, не заходя
по SSH.

Реализуемо на наших данных: DNS-слой наш, правила наши, выбор узла отдаёт
балансировщик, задержки отдаёт observatory. Ничего доизобретать не нужно —
нужно связать и показать.

Обратный разбор тоже полезен: показать домены, которые ушли **не туда**,
куда пользователь ожидал, — например, попали в туннель, не попав ни в один
список.

## Канарейка на экране

Одна строка, которую не показывает ни один роутер в мире:

```
Провайдер подменяет DNS-ответы.
Выучена заглушка 46.191.166.9, отбраковано 1 284 ответа за сутки.
```

Это не метрика, это открытие. Человек узнаёт про свою сеть то, чего не знал,
и видит, что устройство с этим уже справляется.

## Экономия вместо расхода

Ту же цифру распределения стоит подать с другой стороны:

```
Через туннель прошло 19%.
Без распределения ушло бы 100% — сэкономлено 10.0 ГБ за сутки.
```

Для владельца, платящего за серверы, это единственное число, которое имеет
денежное выражение.

## Дисциплина

Реакция «моё почтение» возникает от **немногого, сделанного глубоко**.
Стена виджетов даёт обратный эффект: чем больше показано, тем меньше
замечено.

Три вещи выше — разбор маршрута, Канарейка, экономия — сильнее, чем
пятнадцать блоков со счётчиками. Всё остальное раскрывается по требованию,
а не занимает главный экран.

## Чего не делать

**Не утверждать причину, которую система не установила.** За одну сессию
работы над podkop это чинилось трижды: «не удалось выполнить» вместо разбора,
«вероятно, не хватает места» там где места хватало, красный FakeIP при
полностью работающем туннеле.

Если причина неизвестна — так и писать, и показывать, что именно проверялось.

**Не показывать зелёное там, где не проверяли.** Недоступность внешнего
сервиса проверки ничего не говорит о самом механизме. Это состояние
«проверить не удалось», а не «сломано».

**Не смешивать «команда отработала» и «всё хорошо».**

## Два интерфейса, одна модель

**Панель клиента** — подписка и привязки. Ничего больше: ни DNS,
ни интерфейсов, ни списков.

**LuCI** — всё остальное, с уровнями видимости: обычный, расширенный,
эксперт.

Данные оба берут через CLI xkop, а не напрямую из движка. Формат Xray
и адрес его эндпоинта не должны быть известны ни одному интерфейсу —
см. `cli-contract.md`.

## Источник данных

Метрики Xray по `http://127.0.0.1:11111/debug/vars`, обычный JSON:
счётчики трафика по исходящим и `health_ping` по узлам.

Одна команда CLI отдаёт это в нормализованном виде. Опрос по требованию
и с шагом, достаточным для живого экрана, но не нагружающим роутер.
